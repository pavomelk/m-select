# m-select Requirements v2

> Restructured, consolidated version of `requirements.md`.
> Each requirement carries a stable ID for reference from tests, use-cases and code.

---

## 1. Document conventions

### 1.1 Requirement ID scheme
- ID: `REQ-<section>-<nn>` (e.g. `REQ-3.1-01`).
- IDs are stable once assigned.
- Cross-references use section numbers.

### 1.2 Priority
- `P0` – must have | `P1` – should have | `P2` – nice to have | `TBD` – undecided

### 1.3 Status
`Draft` → `Detailed` → `Agreed` → `Implemented`

### 1.4 Glossary
| Term | Meaning |
|---|---|
| *Selection Box* | Always-visible part of the control |
| *Drop Down* | Collapsible part containing the *Items* |
| *Item* | A selectable option / entry in the hierarchy |
| *Root Container* | The single root of the *Items* hierarchy — a separate Array-like object (not an *Item*) that is the parent of all top-level *Items* |
| *Chip* | Visual representation of a selected *Item* in the *Selection Box* |
| *Collapsed Chip* | A single chip that indicates the number of selected *Items* |
| *Filter* | Text input narrowing the scope of shown *Items* |

---

## 2. Overview / purpose
- The component provides the possibility to make multiple-choice selection of pre-defined options on a web page.
- It implements an extended combobox + listbox pattern whose flexibility provides various modes of navigation and feedback.

## 3. Component model

### 3.1 Architecture / lower-level parts
- [ ] `REQ-3.1-01` The component consists of an always-visible *Selection Box* and a collapsible *Drop Down*. *(P0)*
- [ ] `REQ-3.1-02` It has an *Items* component implementing the Composite pattern over individual *Item* objects. *(P0)*
- [ ] `REQ-3.1-03` Each *Item* object maintains its representation in the document as both "Item" and "Chip". *(P0)*
- [ ] `REQ-3.1-04` It has a *Selection Box* object and a *Text* input object. *(P0)*
- [ ] `REQ-3.1-05` Lower-level parts provide clear separation of concerns yet interact with each other. *(P1)*
- [ ] `REQ-3.1-06` *Items* are implemented with the Composite pattern; navigation and selection logic is shared within the composition. *(P1)*
- [ ] `REQ-3.1-07` The *Items* hierarchy is rooted in a *Root Container* — a separate Array-like object (not an *Item*) that serves as the parent of all top-level *Items*. *(P0)*
- [ ] `REQ-3.1-08` The *Root Container* is the only node without a parent; every *Item*'s parent is either the *Root Container* (top-level) or an owning *Group Item*. *(P0)*
- [ ] `REQ-3.1-09` The *Root Container* provides the owner interface its *Items* require: an `element` (the node the top-level *Item* views attach to), `depth = -1`, and array-like access (numeric keys, `length`, iteration) over its top-level *Items*. *(P0)*

### 3.2 Item
- [ ] `REQ-3.2-01` An *Item* presents a user selection. *(P0)*
- [ ] `REQ-3.2-02` *Item* states (mutually exclusive): `[unselected – selected]`. If selected → a *Chip* is placed in the *Selection Box*. A *Group Item* is never selected in its own right, so it is the exception and owns no *Chip* (REQ-3.3-04). *(P0)*
- [ ] `REQ-3.2-03` *Item* kinds (mutually exclusive): `Group Item` (contains children) or `Leaf Item`. *(P0)*
- [ ] `REQ-3.2-04` *Item* value (mutually exclusive): `has value` or `has no value`. A *Leaf Item* with a value can be selected; a *Group Item* cannot, whatever value it carries (REQ-3.3-04). An *Item* with no value is visually present only. *(P0)*
  - `undefined` (absent), `null` and the empty string are all read as "no value": they are not values in their own right, so such a *Leaf Item* is not selectable and owns no *Chip*. `0` and `false` are real values and are kept. The same three spellings are treated as "no value" by duplicate detection (REQ-3.2-12).
- [ ] `REQ-3.2-05` Non-mutually-exclusive states can be combined unless stated otherwise. *(P1)*
- [ ] `REQ-3.2-06` Every item can be navigated to with mouse and keyboard. *(P0)*
- [x] `REQ-3.2-07` An *Item* may optionally be given a `tooltip` property; when present its text is rendered as the native tooltip (HTML `title` attribute) on both the *Item* DOM element and its *Chip* DOM element. The property is named for what it produces rather than for the HTML attribute that carries it, which is an implementation detail of the browser's own tooltip. Default: omitted, no tooltip. *(P2)*
- [ ] `REQ-3.2-08` *Item* `parent` is a required constructor argument, fixed at construction: the *Root Container* for top-level *Items*, an owning *Group Item* otherwise. There is no parent-less *Item* inside a component. *(P0)*
- [ ] `REQ-3.2-09` An *Item* attaches its own view into `parent.element` by itself during construction (child-side attach); the parent does not append its children. *(P0)*
- [ ] `REQ-3.2-10` *Item* depth = `parent.depth + 1`; top-level *Items* are at depth 0 because the *Root Container* reports depth −1. *(P0)*
- [ ] `REQ-3.2-11` *Item* `selectable` is a boolean, defaulting to `true` when absent, so a *Leaf Item* is selectable when it has a value and does not set `selectable: false` (REQ-3.2-04). A spec is not rejected for a spelling the component can read correctly, but an authoring mistake is reported: a `selectable` that is neither a boolean nor read as false (`0`, `'FALSE'`, `'yes'`) warns, because the author's intent and the component's reading have parted ways; and a `selectable` read as true on an *Item* with no value warns, because there is nothing to select (`selectable: false` on a valueless *Item* is not reported, since it agrees with the missing value). The string `'false'` is honoured, since an HTML attribute or URL parameter arrives as a string, and warns no more than `false` does. These are diagnostic only — the reading is unchanged. *(P1)*
  - Spec warnings are emitted while *Items* are built, before a control exists to carry them, so they default to visible (`warn`) rather than following the otherwise-silent component logger; an explicit `options.logLevel` governs them too, so `'silent'` means silent.
- [ ] `REQ-3.2-12` *Item* values are unique across the tree: two *Items* may not declare the same value, and construction throws otherwise. *Items* with no value are skipped, since there is nothing to collide on. *(P0)*

### 3.3 Group Item
- [ ] `REQ-3.3-01` A *Group Item* contains other items (Child Items). *(P0)*
- [ ] `REQ-3.3-02` It toggles the selection of the selectable *Leaf Items* it contains, not a selection of its own: a *Group Item* is a container, not a selectable unit, so its `selected` state is derived from the count of selected selectable descendants (`selectedCount > 0`) and is never set independently. Which of its children a prompted toggle reaches is the `groupItems.toggleScope` question of REQ-3.3-03. *(P0)*
- [ ] `REQ-3.3-03` A prompted toggle on a *Group Item* — `Space`/`Enter` in the *Drop Down*, or a click — cascades to its selectable descendants per `groupItems.toggleScope` (REQ-5-05), independent of whether a filter query is active: `'all'` reaches every descendant, `'visible'` only those not currently hidden (`visible`). A hidden child is skipped under `'visible'` however it came to be hidden; a filter query is one way, not the condition. This is a different question from what a filter reveals, which is `groupItems.filterScope` (REQ-5-06). The unprompted tri-state act of REQ-3.3-09 reads the same `toggleScope`. *(P0)*
- [ ] `REQ-3.3-04` A *Group Item* owns no *Chip* of its own, whatever value it carries. A `selected: true` flag on a *Group Item* spec is shorthand for selecting all of its selectable descendants; it does not make the *Group Item* itself a selection unit. *(P0)*
- [ ] `REQ-3.3-05` It can align its children in a column or row, per options for that hierarchy level: `align` is keyed by the depth of the *Items* being laid out (0 = top level), each entry taking either the shorthand `'row'`/`'column'` or an object `{ flow }`. Alignment is presentation, not behaviour: it names the axis that walks the level (`ArrowLeft`/`ArrowRight` on a row, `ArrowUp`/`ArrowDown` on a column) and leaves the other pair to change depth — it never changes *where* a movement goes, only which keys make it — see `REQ-3.11-14.1`. *(P1)*
- [ ] `REQ-3.3-06` It may contain nested group items; notably one "master" group can allow selection of all *Items* in the *Drop Down*. *(P2)*
- [ ] `REQ-3.3-07` Its visual representation includes a "partial selection" state for when only some of its children are selected. *(P0, sentence in source cut off — see 11)*
- [ ] `REQ-3.3-08` `selectedCount` and `selectableCount` are counts maintained per *Group Item* — accumulated as the tree is built and adjusted as each *Leaf Item* is selected — rather than recursive sums recomputed on each read. This keeps a *Group Item*'s `selected` flag, tick state, `inSelection` test, and restricted-list membership (REQ-3.11-21) O(1) regardless of tree depth, so that selection state is never recomputed per-render for large numbers of selected items. *(P0)*
- [ ] `REQ-3.3-10` Each *Group Item* maintains a count of the selectable Leaf descendants currently visible, and a count of those already selected, so the tri-state of REQ-3.3-09 is read from two counters rather than by walking the subtree. Both are kept up to date by the `visible` and `selected` setters, each reporting the change up the chain of parents; a write that does not change a flag reports nothing, so a filter pass — which assigns visibility to every *Item* — cannot inflate them. Visibility is per-*Item* and not inherited: a hidden *Group Item* keeps counting the descendants that are themselves visible, because that is the flag a cascade reads as it reaches each child. A *Leaf* that cannot be selected is counted by neither. *(P1)*
  - The selected half cannot be read from `selectedCount`: a picked *Item* the filter has hidden is still in `selectedCount` and is not in what the user can currently reach.
- [ ] `REQ-3.3-11` The root container maintains every *Item* under it in tree order as one array, and an *Item*'s place in that array is its `definitionIndex`, which is what `chipPlaceOrder: 'asDefined'` sorts by (REQ-5-02). The array is updated where the tree is changed rather than rebuilt per read, so ordering an *Item* against another is a number comparison and the flat order cannot describe a tree other than the one on screen. Its one obligation is that every change to the shape of the tree goes through the call that updates it: a top-level *Item* registered at runtime joins the array and is renumbered from that point, and inserting one ahead of another brings the child list, the flat order, `definitionIndex` and the *Drop Down* DOM into line together. Nesting an *Item* inside an existing *Group Item* is deliberately not offered here — it would also have to recount the visibility and selection counters up the chain of parents (REQ-3.3-10) — so it belongs to a method on the *Group Item* itself. *(P1)*
- [ ] `REQ-3.3-09` Toggling a *Group Item* without an explicit state is the tri-state act its tick invites: when every selectable descendant within reach is already selected it unselects them, and otherwise it selects the rest. "Within reach" is the population the cascade acts on, so under `toggleScope: 'visible'` (REQ-3.3-03) a hidden child is neither counted nor reached, and a *Group Item* whose visible children are all selected clears even while its tick reads *partial* over the whole subtree. Both branches are answered from the maintained counters of REQ-3.3-10. The *Select All* button (REQ-3.8-06) is deliberately not this rule: it is a flat action over visible *Leaf Items* with no tick to match, so it clears when any of them is selected. *(P0)*

### 3.4 Chip
- [ ] `REQ-3.4-01` A *Chip* is the visual representation of a selected option in the *Selection Box*. *(P0)*
- [ ] `REQ-3.4-02` It can have states *Current* and *Selected*. *(P0)*
- [ ] `REQ-3.4-03` It contains a visual element for removal by mouse; removal leads to unselection of its corresponding *Item*. *(P0)*
- [ ] `REQ-3.4-04` It has two separate mouse click areas: clicking "x" removes/unselects; clicking anywhere else marks it *Current* and enters Chip Navigation Mode (as if `<ArrowLeft>` had been pressed while hovering it), without removing/unselecting. *(P0)*
- [ ] `REQ-3.4-05` Removing a *Current* *Chip* via its "x" hands *Current* to the *Item* that occupies the removed chip's vacated slot once the *Chip* is gone — the one that slides into it from the right, or, when the removed *Chip* was the last, the one that is then the last; the rule is identical in LTR and RTL flow. The answer is asked of the box as it stands after the removal, not of the sequence before it, so "the previous one" is only shorthand for a *Chip* that has by then become the last. Where the *Current* marker and the *Chips* answer this differently is settled by `REQ-3.11-27`. When no *Chip* is left there is no slot to fill, so the marker stays on the *Item* that was just unselected rather than being dropped; a *Group Item* is never a *Chip*, so unselecting it as a whole vacates no slot either and likewise leaves *Current* where it is. *(P0)*
- [ ] `REQ-3.4-06` Clicking the "x" neither opens the *Drop Down* nor changes the input mode. *(P0)*

### 3.5 Item/Chip entanglement
- [ ] `REQ-3.5-01` Selecting/unselecting an *Item* and its *Chip* is always the same single action, regardless of which of the two the user interacted with. *(P0)*
- [ ] `REQ-3.5-02` Only one of the two is ever the live keyboard-navigation target at a time, but the highlighted state should not be effectively siloed to one side — the component communicates which of an *Item*/*Chip* pair, and which of *Selection Box*/*Drop Down*, currently owns the user's attention. *(P0)*
- [ ] `REQ-3.5-03` Navigation lets the user move fluidly between acting on *Chips* and acting on *Items* without losing their place: leaving one side (closing *Drop Down*, or exiting the list of *Chips*) while the underlying selection is still relevant hands control to the other side's matching representation of that same selection. *(P0)*

### 3.6 Visual similarity
- [ ] `REQ-3.6-01` *Items* and *Chips* contain main uniform elements with visually similar appearance, sharing common style options unless there is justified need for a new style; each state must be clearly distinguishable. *(P1)*
- [ ] `REQ-3.6-02` *Items* and *Chips* share visual similarities as much as possible; their differences are justified by functional requirements. *(P1)*
- [ ] `REQ-3.6-03` Example state styles: "selected", "inactive", "unselectable", "group-item", … *(P2)*
- [ ] `REQ-3.6-04` *Chip* removal element is visually similar to "x". *(P1)*
- [ ] `REQ-3.6-05` Selected *Items* show a "tick"; for *Group Items*, partial selection is the same tick with reduced opacity. *(P1)*
- [ ] `REQ-3.6-06` *Current Item* is visually distinguishable. *(P1)*
- [ ] `REQ-3.6-07` *Chip Items* are navigable and visually distinguishable. *(P1)*
- [ ] `REQ-3.6-08` The active input mode is visually distinguishable. The root element carries it as `cm-select--mode-<mode>`, exactly one such class at a time: set on construction and swapped over on every real transition, the initial *Filter mode* being set without a transition of its own. It is the mode the class names rather than the *Drop Down* being open that a style keys on, because the *Drop Down* is open in *Chip* and *Collapsed mode* too — between the press that opens it and the one that hands over to *DropDown mode* (`REQ-3.11-12`) — so the open state on its own does not say that *DropDown mode* is the active one. Of the modes, *DropDown mode* is the marked one: the keyboard has left the *Selection Box* and gone into the list, so the *Chips* are held back from the foreground. It is the *Chips* and not the whole *Selection Box* that are held back, the *Filter* keeping the system focus for the whole session (`REQ-3.11-03`) and being dimmed with the box otherwise. *(P1)*

### 3.7 Selection Box
- [ ] `REQ-3.7-01` Always-visible part of the control. *(P0)*
- [ ] `REQ-3.7-02` Displays currently selected *Items* in the form of *Chip Items*. *(P0)*
- [ ] `REQ-3.7-03` Captures focus into the *Filter*. *(P0)*
- [ ] `REQ-3.7-04` Contains a visual area that allows removal of all selected items. *(P0)*
- [ ] `REQ-3.7-05` May "collapse" *Chips* into a single *Collapsed Chip* indicating the number of selected *Items* (details via `maxVisibleChips`):
  - If option disabled → all *Chips* are shown as usual. *(P1)*
  - If enabled by `maxVisibleChips`: individual *Chips* are shown while count ≤ `maxVisibleChips`; once count exceeds it, all are replaced by one summary *Chip* labeled "<Number> items selected", which stands for the whole selection rather than for any one *Item*. *(P1)*
  - The summary *Chip* is handled as any other *Chip*: the removal keys act on it as they would on a *Chip* of its own — `BackSpace` / `Delete` while it is *Current*, or `BackSpace` at the leftmost caret in *Filter* mode. Since it stands for the selection as a whole, acting on it unselects every selected *Item*, after which the box expands and the keyboard is back in *Filter* mode. *(P1)*
  - The summary *Chip* carries the "(x)" removal area any other *Chip* has, which removes the whole selection; the rest of it is a toggle for the *Drop Down*, opening it when closed and closing it when open. *(P1)*
  - The summary *Chip* shows the *Current* marking — it looks like the *Current Chip* — but that marking is its own and moves nothing: the logical *Current* the control keeps is a marker over an *Item* only, and this *Chip* is no *Item*. So opening the *Drop Down* from it seeds that marker on the first visible *Item* rather than on the summary *Chip*, and the two readings never disagree because there is only one of them. The marking is the one class a *Current Chip* of any kind carries, so the stylesheet gives it the same look it gives an individual *Chip*; it is held while *Collapsed mode* is engaged and dropped on leaving it, so the summary *Chip* is never marked in *Filter* mode. *(P1)*
- [ ] `REQ-3.7-06` The *Control* sets no width of its own: it fills the width its containing element gives it, so an application can size it by styling the container. *(P1)*
- [ ] `REQ-3.7-07` The *Selection Box*'s list of *Chips* is derived from the selected state of the *Items* rather than maintained alongside it, so it cannot fall out of step with the box across an addition, a removal or a re-render. It holds the *Chip* representation of each such *Item*; a *Group Item* is never selectable in its own right, so it owns no *Chip* and is left out (REQ-3.3-04). The list serves two purposes: it is the visual indication of the current selection whenever the *Drop Down* is closed, and it is what the user navigates the selection by in *Chip mode* — clicking a *Chip* makes it *Current*, the arrow keys move *Current* between *Chips*, and a *Chip* is removed either by clicking its dedicated (x) area or with the `BackSpace` / `Delete` keys, that keyboard scenario being the one of a text caret in `<Insert>` mode. Its order is the one REQ-5-02 asks for, `unsorted` being the order in which the *Chips* arrive in the box, the most recently selected *Item* at the tail. While the box is collapsed the list still holds the *Chips* the *Collapsed Chip* stands for, which is what lets the box expand again without rebuilding its membership. *(P1)*
- [ ] `REQ-3.7-08` Allows arrow navigation between chips and selective removal via `BackSpace` and `Delete` keys, as well as mouse clicks in their dedicated removal area; while the selection is collapsed these keys act on the summary *Chip*, which removes the selection as a whole rather than a single *Item* (REQ-3.7-05). *(P0)*

### 3.8 Drop Down
- [ ] `REQ-3.8-01` Contains selectable *Items*. *(P0)*
- [ ] `REQ-3.8-02` Appears and disappears depending on user actions. *(P0)*
- [ ] `REQ-3.8-03` Allows navigation between selectable *Items* with arrow keys. *(P0)*
- [ ] `REQ-3.8-04` Does not interfere with the appearance of other elements on the page, including other *Control* instances. *(P0)*
- [ ] `REQ-3.8-05` Clicking an *Item* toggles its selection — the same single action as its *Chip* (REQ-3.5-01) — and marks it *Current*. *(P0)*
- [ ] `REQ-3.8-06` The *Drop Down* offers a *Select All* button that toggles the selection of the *visible* selectable *Leaf Items* only, a *Group Item* being a container rather than a selected unit (REQ-3.3-04): when any of them is selected it unselects them, otherwise it selects them; *Hidden* (filtered-out) *Items* are left untouched, *Chips* always mirror the resulting selection, and the action clears the *Filter* query, as committing a single *Item* with `Enter` does (REQ-3.11-18). *(P0)*
- [ ] `REQ-3.8-07` The *Select All* button appears only while the *Filter* query is active (non-empty text) **and** more than one selectable *Leaf Item* is visible; a query leaving a single result — or none — hides it, since bulk-selecting would merely repeat that one *Item*'s toggle (or do nothing at all). Clearing the query hides it again. *(P0)*

### 3.9 Filter
- [ ] `REQ-3.9-01` Editable element that allows text input. *(P0)*
- [ ] `REQ-3.9-02` Entered text is used to filter available *Items* in the *Drop Down*. Modifying the text — the first keystroke included — opens the *Drop Down* at once, since wanting to filter is wanting to see the list; a programmatic query write is not a user edit and leaves the open state alone. *(P0)*
- [ ] `REQ-3.9-03` Whether an *Item* matches the query is one decision, taken by a matching function: by default the *Item*'s *Label* contains the query, case-insensitively, and an application may replace that decision with its own through the `filterFn` option (REQ-5-09). The function answers for one *Item* at a time — given the *Item* and the query exactly as typed, case preserved and nothing trimmed — so it can match on the value, a prefix, a regular expression, or a list of synonyms the application keeps beside the control, while everything else about a query stays the component's: the debounce, the *Drop Down* opening on the first keystroke (REQ-3.9-02), and the re-homing of the *Current* marker (REQ-3.11-19). It is asked about *Group Items* as well as leaves, because a *Group*'s own match is what `groupItems.filterScope` reads (REQ-5-06). *(P1)*
- [ ] `REQ-3.9-04` An empty query filters nothing: with no text in the *Filter* every *Item* is visible, and a custom matching function is not consulted at all. The query is what narrows the list, so no text is no narrowing; a matcher is not a second, permanent filter that the text merely adjusts. The selected-*Items*-only restriction is not a query — it is a population of *Items* — so it keeps its own matcher and is applied whatever the text (REQ-3.11-24). *(P0)*
- [ ] `REQ-3.9-05` A custom matching function replaces the matching decision and nothing else: `groupItems.filterScope` still says whether a matching *Group Item* shows all of its children or only the children that match themselves, and a non-matching *Group* still stays visible while one of its children does (REQ-5-06). The function's answer is read as a boolean, so a truthy value counts as a match. *(P1)*

### 3.10 Modes of interaction
- [ ] `REQ-3.10-01` *DropDown mode* — user selects *Items* by navigating the *Drop Down* (open). *(P0)*
- [ ] `REQ-3.10-02` *Filter mode* — user enters text to narrow down the selection range (open). *(P0)*
- [ ] `REQ-3.10-03` *Chip mode* — user navigates *Chips* (open or closed). *(P0)*
- [ ] `REQ-3.10-04` *Collapsed mode* — user navigates *Items* when there is a *Collapsed Chip* (open or closed). *(P1)*
- [ ] `REQ-3.10-05` Clicking the *Filter* input enters *Filter mode* and opens the *Drop Down*; the input caret is enabled. *(P0)*
- [ ] `REQ-3.10-06` Clicking a *Chip* enters *Chip mode*, marks that *Item* *Current* (reflected in the *Drop Down* and scrolled into view) and opens the *Drop Down*; the caret is hidden. *(P0)*
- [ ] `REQ-3.10-07` Clicking the *Collapsed Chip* enters *Collapsed mode*, restricts the *Drop Down* to the selected *Items* and opens it; the caret is hidden. *(P0)*
- [ ] `REQ-3.10-08` Clicking *Remove all* clears the selection and the *Current* *Item*, removes every *Chip*, enters *Filter mode* and opens the *Drop Down*. *(P0)*
- [ ] `REQ-3.10-09` Clicking elsewhere inside the *Selection Box* enters *DropDown mode* and opens the *Drop Down*. *(P0)*
- [ ] `REQ-3.10-10` Clicking outside the *Control* closes the *Drop Down*, reverts to the default *Filter mode* and hides the caret. *(P0)*
- [ ] `REQ-3.10-11` *Filter mode* is the default mode; every user action dispatches a mode change. *(P0)*
- [ ] `REQ-3.10-12` The *Modes* object is not part of the public API; tests observe mode switches through an exported symbol. *(P0)*

### 3.11 Keyboard interaction
- [ ] `REQ-3.11-01` The *Control* is one Tab stop taken as a whole — *Selection Box* and *Drop Down* together, the *Drop Down* open or closed — and never one Tab stop per part of it. So wherever a requirement speaks of leaving or entering "the component" it means all of it, *Drop Down* included: a press of `Tab` never moves the focus from one part of the *Control* to another, and in particular never into an open *Drop Down*, whose *Items* are no more Tab-reachable than its buttons are (REQ-3.11-02). `Tab` is the page's key at both ends instead: it arrives in the *Filter* from the element before the *Control* and leaves to the element after it, `Shift+Tab` doing the same backwards, in one press each way — a user can walk the whole page past the *Control* without ever being stopped inside it twice, and the focus never rests on anything but the *Filter*. *(P0)*
  - *DropDown mode* is the one mode that holds the key rather than let it out, and the rule there is about what `Tab` may not do while the keyboard is working inside the *Control*. In that mode the keys act on the list while the system focus still sits in the *Filter* (REQ-3.11-03), so a `Tab` left to the browser would take the focus out of the *Control* from underneath an interaction that is still in progress; `Tab` and `Shift+Tab` are consumed instead, which leaves the focus on the *Filter*, the mode, the open *Drop Down* and the *Current* mark exactly as they were. Leaving the list is then a deliberate act — `Escape` (REQ-3.11-11) or `Enter` (REQ-3.11-18) — after which the *Control* is in *Filter mode* again and `Tab` leaves it as above. That the trigger is the mode and not the *Drop Down* being open is the difference from *Chip* and *Collapsed mode*, where the *Drop Down* is open too but the keyboard is still on the *Chips*: there `Tab` leaves the *Control* normally.
  - The rule in one line: `Tab` is the way out of the *Control*, never the way through it — no *Chip*, *Item*, button or chip "x" is ever reached by it, whichever of them are on screen — and while *DropDown mode* holds the keyboard, `Tab` does nothing rather than moving the focus anywhere.
- [ ] `REQ-3.11-02` The following parts are not Tab-reachable (`tabindex="-1"`): *Remove all* button, *Select All* button, and every chip "x". They remain clickable and programmatically focusable. *(P0)*
- [ ] `REQ-3.11-03` After the *Drop Down* opens, the arrow keys move a *Current* pointer between Items/Chips without moving the system focus; the *Filter* keeps the focus for the whole session. *(P0)*
- [ ] `REQ-3.11-04` Filter mode is active when the component receives focus: focusing the *Filter* enters *Filter mode* and enables the input caret. *(P0)*
- [ ] `REQ-3.11-05` In *Filter mode*, `ArrowDown` opens the *Drop Down* when it is closed, enters *DropDown mode*, and applies *DropDown mode*'s own `ArrowDown` movement to the same press: with no *Current Item* it starts on the first visible *Item*, and with one already standing — left by a re-filter (`REQ-3.11-19`) or otherwise — it walks on from it as every later `ArrowDown` does. It reaches *DropDown mode* on the first press where the two *Chip* modes need two (`REQ-3.11-28`). *(P0)*
- [ ] `REQ-3.11-06` In *Filter mode*, `ArrowLeft` with an empty Filter and Chips present enters *Chip mode* marking the rightmost *Chip* *Current* (or *Collapsed mode* with the *Collapsed Chip* *Current* when the selection is collapsed); otherwise it is passed down to the input's default text-caret navigation. *(P0)*
- [ ] `REQ-3.11-07` In *Chip mode*, `ArrowLeft`/`ArrowRight` move the *Current* marker between *Chips*; `ArrowLeft` on the leftmost *Chip* is ignored, `ArrowRight` on the rightmost *Chip* marks nothing *Current*, exits to *Filter mode* and clears the marker on the *Item* and its *Chip*. *(P0)*
- [ ] `REQ-3.11-08` In *Chip mode*, editing keys behave as in text-editing insert mode: `Delete` unselects the *Current Chip* (the marker hands to the following *Chip*, or the preceding one when deleting the last), `Backspace` unselects the *Chip* left of the *Current* one and keeps the marker; with the leftmost *Chip Current* `Backspace` is ignored. *(P0)*
- [ ] `REQ-3.11-09` The *Chip* and *Collapsed* modes operate on Chips: with no Chips left they are not active and fall back to the default *Filter mode*. *(P0)*
- [ ] `REQ-3.11-20` In *Chip mode*, `ArrowDown` opens the *Drop Down* (scrolling the *Current Item* into view) while staying in *Chip mode*; a repeated `ArrowDown`, with the *Drop Down* already open, enters *DropDown mode* and leaves the *Current* marker on that same *Item*, so the list continues from the *Chip* the marker came from. Two presses rather than one, and the reason is in `REQ-3.11-28`. *(P0)*
- [ ] `REQ-3.11-10` In *Filter mode*, `Backspace` with the caret at the text's leftmost position unselects the rightmost *Chip* and stays in *Filter mode*; anywhere else it is left to the input's default text editing. *(P0)*
- [ ] `REQ-3.11-11` `Escape` closes the *Drop Down* in every mode — and in *Filter mode* it is a two-step cancel: with the *Drop Down* open the press only closes it, keeping the query the user may still want, and with it already closed the next press clears the query to `''`, which re-filters the hidden list back to the unfiltered one and re-homes the *Current* marker by the query rule (`REQ-3.11-19`); an empty query leaves the marker alone. The key never opens the *Drop Down*, and the text is cleared through the *Filter*'s own `query`, so the input's value, the list and the marker cannot disagree. In *DropDown mode* it also returns to the mode that was active before it, which is the mode the *Drop Down* was entered from (falling back to *Filter mode* with a logged warning when no previous mode is recorded, which normal flows cannot trigger). A *Drop Down* entered from *Collapsed mode* is the exception and returns to *Filter mode*: `Escape` commits nothing, and the restriction to the selected *Items* exists only so a selection the *Collapsed Chip* hides stays navigable, which a *Drop Down* on its way out no longer needs. So `Escape` drops the restriction, clears the *Current Item* and unmarks the *Collapsed Chip*. *(P0)*
- [ ] `REQ-3.11-12` In *Collapsed mode*, the *Collapsed Chip* carries the *Current* mark only while the mode is active (set on entry, cleared on leaving, including the exit to *Filter mode* on `ArrowRight`); `ArrowDown` opens the *Drop Down* restricted to the selected *Items*, and a repeated `ArrowDown` moves on to *DropDown mode* with that restriction kept, so the selected *Items* are navigable as a list. That handover also starts the *Current* mark on the first navigable *Item* of the restricted list, which no other origin needs an `Item` to carry it in from: without it the list would open with nothing *Current* and `Space` and `Enter` would have nothing to act on. Entering the mode is likewise the end of any *Current Item* mark, which is cleared on entry rather than remembered: the *Collapsed Chip* becomes the only current part, and the mark is started afresh from the top of the restricted list each time the list is entered, so a round trip through *Collapsed mode* returns to the top instead of resuming where the mark stood. Carrying it across would mark two parts current at once - the *Collapsed Chip* and an `Item` of a list that is no longer open. The opening press and the handover press are two acts here as they are in *Chip mode*, and the reason is in `REQ-3.11-28`. *(P0)*
- [ ] `REQ-3.11-28` How many presses of `ArrowDown` it takes to get from a mode into *DropDown mode* is not uniform, and the difference is deliberate rather than incidental. From *Filter mode* one press does it (`REQ-3.11-05`): it opens the *Drop Down*, applies the list's own `ArrowDown` movement to the same press (starting on the first visible *Item* when none is set, walking on from one a re-filter left standing) and enters *DropDown mode* in the same act. From *Chip mode* (`REQ-3.11-20`) and from *Collapsed mode* (`REQ-3.11-12`) it takes two — the first press opens the *Drop Down* and leaves the mode and its own marker exactly as they were, the *Current Chip* still marked in the one case and the *Collapsed Chip* still the only marked part in the other, and the second hands the keyboard over to the list. What separates them is that *Filter mode* is not navigating anything, so `ArrowDown` from it means "into the list", whereas the two *Chip* modes are navigating the selection's *Chips* and their `ArrowDown` is a step out of that navigation: the list is revealed beside the *Chips* first and entered on the press after. The handover press is also where the marker crosses over in both cases — *Chip mode* leaves it on the *Item* the *Chip* it came from stands for, *Collapsed mode* starts it on the first navigable *Item* of the restricted list — while the opening press starts no marker of its own, so no two parts are ever marked current at once. The active mode is visible in the document (`REQ-3.6-08`), which is what makes this something the user can read off the control rather than have to infer. *(P0)*
- [ ] `REQ-3.11-21` While the *Drop Down* is restricted to the selected *Items*, a selection change re-filters it: an *Item* that is unselected (toggled off, deleted as a *Chip*, or unselected directly) disappears from the visible list, and a newly selected one shows up. A *Group Item* qualifies through what it holds, not through its own flag, so a *Group* whose selectable children are all unselected leaves the list too. With a text query instead, a selection change does not re-apply the query, so a *Filter* still waiting on its debounce is not cut short. *(P0)*
- [ ] `REQ-3.11-22` A *Drop Down* entered from *Collapsed mode* holds an achieved collapse for as long as it is active, so unselecting *Chips* down below `maxVisibleChips` does not expand the box under the list being navigated; the hold is released when nothing is selected and when *DropDown mode* is left, and it never *creates* a collapse that was not achieved. *Collapsed mode* itself holds the same way for the duration of its own marker. The hold is implied by the mode the interaction is anchored on (`MSelect.holdsCollapse`) rather than tracked as separate state, so it cannot outlive the modes that justify it. A *Drop Down* entered any other way is not held at all, and the count alone decides — see `REQ-3.11-26`. *(P0)*
- [ ] `REQ-3.11-23` Emptying the selection returns the *Control* to its default state: *Filter mode*, the *Drop Down* no longer restricted to the selected *Items* (so every *Item* is listed again), *Current* left on the *Item* that was just unselected (it is still in the restored list, so the marker is not dropped with the restriction), the caret editable again, and no collapse held. It applies to whatever mode the emptying happened in, including a *Drop Down* left restricted by an emptied selection. *(P0)*
- [ ] `REQ-3.11-24` The *Drop Down* restricted to the selected *Items* stays restricted until nothing is selected — not merely until the count falls back to `maxVisibleChips` — and whichever way the restriction was entered from: the `ArrowDown` handover out of *Collapsed mode*, or a click on an *Item* in that list. Entering *Filter mode* is the only thing that drops it. *(P0)*
- [ ] `REQ-3.11-25` A click on an *Item* that empties the selection stays in *DropDown mode* — only the restriction is dropped — but the list it was aimed at is gone, so the *Current* marker restarts on the first navigable *Item* of the restored list instead of following the clicked one. A click that leaves the selection non-empty marks the clicked *Item* as before. *(P0)*
- [ ] `REQ-3.11-25.1` `Enter` in a *Drop Down* entered from *Collapsed mode* toggles the *Current Item*, closes the list, and then lets the *Collapsed Chip* be judged against what the toggle left behind: while the count is still above `maxVisibleChips` it returns to *Collapsed mode* with the *Current* mark back on the *Collapsed Chip*, and once the count is back within `maxVisibleChips` it ends in *Chip mode* instead, because the box is no longer collapsed and the *Collapsed Chip* has nothing left to stand for. The boundary is the same one the box itself draws, and it is deliberately not the box's `isCollapsed`, which holds an achieved collapse through a count that has come back within the limit. The *Current Chip* is the one the toggle already elected — the chip that took the vacated slot, or the one that is then last, per `REQ-3.4-05` and `REQ-3.11-27` — so `Enter` and `Space` answer the same question the same way in one *Drop Down* rather than each having a rule of its own. When what was toggled is a *Group Item* it owns no *Chip* and vacates no slot, so the marker can be left standing on an *Item* that *Chip mode* has nothing to move between; the *Chip* rule answers for it too, as the next *Chip* along the tree and the last one past them all. *(P0)*
- [ ] `REQ-3.11-26` A *Drop Down* entered from *Chip mode* imposes neither of *Collapsed mode*'s carries-over: it is not restricted to the selected *Items*, and the selection is not held collapsed. The *Collapsed Chip* and individual *Chips* there follow `maxVisibleChips` alone, so a selection within the limit is shown as individual *Chips* and only exceeding the limit collapses it — including from inside that *Drop Down*, where a selection grown past the limit collapses and falls back to individual *Chips* again once it fits. The same holds for a *Drop Down* entered from *Filter mode*. *(P0)*
- [ ] `REQ-3.11-13` Mouse interaction inside the *Control* (clicking a *Drop Down* *Item*, a *Chip*, a button) never moves the system focus away from the *Filter*: the *Filter* keeps its focus for the whole session (REQ-3.11-03) and the *Control* keeps responding to keys afterwards. *(P0)*
- [ ] `REQ-3.11-27` While the *Drop Down* is restricted to the selected *Items*, the *Current* marker never outlives the list it is marking. Unselecting the *Current Item* by `Space` moves the marker on by `nextInLevel`, so the answer is always the *Item's* next sibling, and with nothing after it the answer is the *Item* that is then the last on the axis the removed *Item* stood on. That last step is `previousInAxis`, and it is asked of the axis rather than of the level, because the two differ on a **column**: there the children of a *Group Item* share their *Group's* line, so the *Item* before the last *Group* of a level is that *Group's* last child, while on a **row** the children stand off the line and the *Group* itself is the answer. It is the same question the *Chips* are asked in `REQ-3.4-05`, and the two agree wherever both cover the *Item*. Only the fallback turns on the axis: the forward step skips the removed *Group's* own subtree on either, because toggling it settled that already. A *Group Item* is answered the same way as a leaf, and that is the point: toggling a *Group Item* is an act on the *Group Item*, so its whole subtree is already accounted for and is stepped over rather than walked into. A *Group Item* leaving the list takes its children with it — a child is visible only while every *Item* above it is — so the walk is never in fact choosing between the child and the sibling; the sibling is the answer before the question is asked. This covers the case no *Chip*-side promotion can: a valueless *Group Item* owns no *Chip*, so unselecting it used to leave the marker on an *Item* the restricted list had just stopped showing. An unrestricted list keeps the unselected *Item* visible, so the marker stays on it, and an emptied list is settled by `REQ-3.11-23` instead. *(P0)*
- [ ] `REQ-3.11-14` In *DropDown mode*, list navigation is a structural walk over the rendered, togglable *Items* in **document order**, and no *Item* is ever skipped because of how its level is laid out. Four steps are available, each decided by the *Item* alone: `next` is the first navigable child of a *Group Item*, otherwise the next sibling, bubbling out of a finished subtree to the closest ancestor that has one; `nextInLevel` is that same walk with the *Item's* own subtree stepped over; `previous` is the previous sibling, or the parent when there is none; `descend` is the first navigable child, and `parentNext` the next sibling of the closest enclosing *Item*. The walk has a mirror for the step that follows it in the other direction — `previousInAxis`, which asks the axis rather than the level, and so steps into a previous *Group* on a **column** and not on a **row** — while `previous` stays the backward step of a level, stepping out to the parent at its front. Filtered-out and non-selectable *Items* are not part of the walk and are stepped over; *Group Items* stay reachable. The keys are consumed wherever a *Current* marker exists (the *Filter* is not editable in *DropDown mode*, so there is no caret to hand them back to) and fall through when none does. With no marker set, the keys that walk a level start one, at the first or last navigable top-level *Item* per their direction. *(P0)*
- [ ] `REQ-3.11-14.1` Every level is walked by the axis its own `flow` names, and the *other* pair of arrows is the one that changes depth. The keys are therefore read against the level the marker stands on, never against the key: on a **column** level `ArrowDown` walks forward and `ArrowUp` walks back, on a **row** level `ArrowRight` does and `ArrowLeft` does, and the opposite pair changes level in both cases. Which step a key takes is decided by the pair it belongs to, not by its own name. *(P0)*
- [ ] `REQ-3.11-14.2` Walking a level is forward along it and backward along it, and neither end needs a rule of its own: backward from the first *Item* is its parent, and forward from the last is the parent's next sibling, so the keys that walk a level leave it at either end without any special case. Forward is `next` on a column and `nextInLevel` on a row — the children of a row *Item* sit off the row's own axis, so a *Group* standing in a row is a member of that row to be stepped over rather than an entrance, while the children of a column *Item* sit on that axis and are entered by the same keypress that steps forward. Backward is `previous` on both.
- [ ] `REQ-3.11-14.3` The keys **across** the level's own axis change the depth of the next *Current Item* rather than walking the level. Forwards, a *Group Item* is opened at its first navigable child and anything else steps out to the parent's next sibling — `ArrowRight` on a column level, `ArrowDown` on a row level — so a *Group* can be opened on either pair of arrows. Backwards, the marker goes to the parent — `ArrowLeft` on a column level, `ArrowUp` on a row level. At the top level there is no parent to go back to, and the forward step has nothing left to open, so both are consumed no-ops. *(P0)*
- [ ] `REQ-3.11-14.4` A key with no target leaves the *Current* marker where it is and is still consumed. `Home`/`End` and `PageDown`/`PageUp` (a page of ten) move within the marker's own level rather than over the flattened tree. *(P0)*
- [ ] `REQ-3.11-15` In *DropDown mode*, `SpaceBar` toggles the selection of the *Current Item* — a *Group Item* toggles its descendants per its `toggleScope` (REQ-3.3-03) — while the *Drop Down* stays open and the mode stays active; with no *Current Item* the key is consumed without effect. In the *Chip*-slot sense, unselecting a *Group Item* vacates no *Chip*, so the *Current* marker is not handed to a surviving *Chip* and only a *Chip* that leaves the box promotes its successor. That is the unrestricted answer: while the *Drop Down* is restricted to the selected *Items*, the unselected *Item* leaves the list, and the marker is moved on per REQ-3.11-27 rather than left where it is. *(P0)*
- [ ] `REQ-3.11-18` In *DropDown mode*, `Enter` toggles the selection of the *Current Item*, clears the *Filter* query, closes the *Drop Down* and returns to the mode that was active before it (falling back to *Filter mode* as REQ-3.11-11); with no *Current Item* it toggles nothing, still clears the query and still closes the *Drop Down*. The query goes because `Enter` is the act that says "this is the one": a query is how the *Item* was found, and once it is picked the query has done its work, so leaving it behind would hand back a *Filter* still narrowed to a list the user is no longer looking at, and a *Drop Down* that reopened on that leftover narrow list. It is the same clearing the *Select All* button performs (REQ-3.8-06), and it belongs to this commit rule rather than to this mode's use of it: the two other paths that commit through the rule — `Enter` in *Filter mode* (REQ-3.11-29) and `Enter` in a *Drop Down* entered from *Collapsed mode* (REQ-3.11-25.1) — clear the query as well. Clearing is a query change like any other and re-filters like one (REQ-3.11-19), but the list is closing in the same act, so there is nothing for that rule's re-homing to act on; the *Current* marker is settled by entering the mode the *Drop Down* returns to instead (REQ-3.11-17). *(P0)*
- [ ] `REQ-3.11-29` In *Filter mode*, `Enter` applies *DropDown mode*'s own commit rule (`REQ-3.11-18`) to the *Current Item*: it toggles that *Item* (a *Group Item* per its `toggleScope`, `REQ-3.3-03`), closes the *Drop Down* and leaves the control in *Filter mode* with the *Filter* query cleared by that same rule, which is to say that committing an *Item* here never leaves a narrowed list behind either. With no *Current Item* it selects nothing and still closes. The key is always consumed, so it never reaches an enclosing form's implicit submission. As with `ArrowDown` (`REQ-3.11-05`), the press is handed to *DropDown mode*'s handler after the switch rather than answered by a second copy of the commit rule. *(P0)*
- [x] `REQ-3.11-19` A change of the text query re-homes the *Current* marker, because a re-filter rewrites the list the marker is marking. Every query change puts the marker on the first selectable leaf of the new list, in tree order; a query that leaves nothing visible drops the marker. The marker is **not** kept on an *Item* that happens to survive the query, even though the old query's list had it standing there: the list under a new query is a different list, and after a replacement — `le` typed over with `nd` — an *Item* the two queries share (a *Group* kept visible by a child, or a *Label* matching both) would otherwise hold the marker while the list the user is reading starts somewhere else. The target is a leaf rather than the first row because a *Group* row a query leaves standing is usually kept only by the descendant that matched: in the demo tree `nd` leaves *Cities* visible through *London*, and the *Item* the user is looking at when they press `Enter` is *London*, not the container. A *Group* the query matched by its own *Label* may show no leaf at all under `groupItems.filterScope: 'matching'`; there the marker falls back to the first navigable *Item*, so it does not vanish from a list that still has a row to act on. This is the query's own rule and not a mode's, so it applies wherever the query can change — which is *Filter mode*, and there whether the *Drop Down* is open or closed — and it is why a marker can already stand on an *Item* before `ArrowDown` is pressed (`REQ-3.11-05`, `REQ-3.11-16`). The restriction to the selected *Items* is a re-filter too but is not this rule: it has one of its own (`REQ-3.11-27`) and a selection change never re-homes the marker this way. *(P0)*
- [ ] `REQ-3.11-16` Clicking the *Filter* opens the *Drop Down* without setting any *Current* marker of its own (list navigation starts from the marker `REQ-3.11-19` may already have left on a query, or otherwise only from *DropDown mode* via `ArrowDown`); clicking it again while the *Drop Down* is already open leaves any *Current* marker untouched. *(P0)*
- [ ] `REQ-3.11-17` Entering *Filter mode* clears the *Current* marker: returning to *Filter* from *DropDown mode* (`Escape`), from *Chip*/*Collapsed mode* (`ArrowRight`) or through a normalize fallback never leaves a *Chip* or *Item* marked *Current*. *(P0)*

## 5. Configuration options
- [ ] `REQ-5-01` Placeholder text for the *Filter* input. *(P1)*
- [ ] `REQ-5-02` *Chip* placement order: `unsorted` (default) / `asDefined` / `alphabetical`. `unsorted` is the order the *Chips* arrive in the *Selection Box*, the most recently selected *Item* at the tail, so an *Item* unselected and selected again moves to the tail. A selection preset at instantiation arrives in definition order when seeded from `selected: true` flags, and in the order the array gives when seeded from `selectedValues` (REQ-7-20); with the flags, `unsorted` therefore yields the same order as `asDefined`. `asDefined` is the order the *Items* take in the *Drop Down*, `alphabetical` their *Label* order. *(P1)*
  - `asDefined` is a whole-tree order, not a per-level one: a nested *Item* takes its place among all *Items* as the tree holds them, so an *Item* nested under a *Group Item* defined late cannot sort ahead of a top-level one defined early (REQ-3.3-11).
- [ ] `REQ-5-03` Maximum height the *Drop Down* unfolds to, specified in heights of *Item*. *(P1)*
- [ ] `REQ-5-04` Alignment of items on a specific level (each level can be horizontal or vertical toward its siblings). Keyed by the depth of the *Items* being laid out (0 = top level), an entry being the shorthand `'row'`/`'column'` or `{ flow }`. Alignment only selects which arrow keys walk the level; it does not decide where a movement goes — see `REQ-3.11-14`. *(P1)*
- [ ] `REQ-5-05` `groupItems.toggleScope` — what a toggle on a *Group Item* reaches, read when the user acts: cascade to every child regardless of visibility (`'all'`), or to only those currently visible (`'visible'`, default). The default answers the case of a filter applied on purpose: the user then means to select what fits the query, not the whole subtree. It does not affect a *Group*'s own `selected`/`partial` tick indicator, which always considers every selectable child regardless of visibility. *(P0)*
  - The tick and the tri-state act (REQ-3.3-09) therefore answer different questions, and may disagree: a *Group Item* is `all` only when every selectable descendant is selected, while a click reads only what is reachable. So a *Group Item* whose visible children are all picked can still tick *partial* — a hidden, unselected child keeps it there — and clicking it clears rather than selecting anything again. Both are correct about their own question.
- [ ] `REQ-5-06` `groupItems.filterScope` — what filtering reveals, read when the query changes: a *Group Item* that matches keeps all its children visible (`'all'`, default), or keeps only the children that match the query themselves (`'matching'`). It is read the same way whichever matching function decided the match, the built-in label match or an application's `filterFn` (REQ-5-09). *(P0)*
  - The two are separate options and the application chooses the combination: they answer different questions at different moments (REQ-5-05 what a click reaches, REQ-5-06 what a match reveals), so `filterScope: 'matching'` with `toggleScope: 'visible'` filters a subtree down and then selects the survivors. Their vocabularies differ on purpose — a child can be visible because its *Group* matched without matching the query itself, so "visible" is no filtering answer the way "matching" is no toggling one.
- [ ] `REQ-5-07` `maxVisibleChips` — max number of *Items* selectable and represented by individual *Chips* before a *Collapsed Chip* is shown (default: disabled). *(P1)*
- [ ] `REQ-5-08` Log level — feed for the internal logging (see 8). *(P1)*
- [ ] `REQ-5-09` `filterFn` — the function that decides whether an *Item* matches the *Filter* query, `(item, query) => boolean`; default: absent, meaning the built-in *Label*-contains match (REQ-3.9-03). It is given the *Item* and the query as typed, and is asked about *Group Items* too. It replaces only the matching decision: an empty query still shows everything and is not put to it (REQ-3.9-04), `groupItems.filterScope` still says what a matching *Group* reveals (REQ-5-06), and the query's re-homing of the *Current* marker is unchanged (REQ-3.11-19). *(P1)*
  - The option has two readings — a function, or none — and `null`/`undefined` are how "none" is meant. Anything else is an authoring mistake, reported once when it is read (REQ-3.2-11) and read as none: the option comes from application code, and a wrongly-typed value should leave a working control with the built-in match rather than a page that throws. The *Item* handed to the function is the control's own representation, so it is for reading (its `label`, `value` and place in the tree), not for keeping or writing: changing what an *Item* is stays the component's business.
  - Replacing it at runtime is the other half of `REQ-6-02`: assigning it re-derives the visible list from the query the *Filter* already holds and re-homes the *Current* marker to what the new function left visible, exactly as a query change does (REQ-3.11-19). While the *Drop Down* is restricted to the selected *Items*, that list is what is on screen, so the restriction is re-applied instead and the new function waits for the next query — the restriction keeps its own matcher and its own marker rule (REQ-3.11-27).

- [x] `REQ-7-08` Selection values are passed as part of the form data on submit. *(P0)* — with `options.name` set, one hidden `<input>` per selected *Item* carries that name verbatim and the *Item*'s value, emitted in `selectedValues` order, so the server receives repeated entries (`name=v&name=w`) and joins them as it sees fit. Without `name` the control takes no part in submission. A value containing a comma — the delimiter such a join relies on — is still submitted verbatim but logged once as ambiguous; the *Filter* input is never named.
- [ ] `REQ-7-09` The component supports keyboard and mouse interaction as described in use-case scenarios. *(P0)*
- [ ] `REQ-7-10` The *Drop Down* does not interfere with the appearance of other elements on the page, including other instances. *(P0)*
- [x] `REQ-7-11` Events are produced upon basic user actions: toggle, leave, opening *Drop Down*, etc. *(P0)* — a toggle and a bulk selection change emit `cm-selection-change`, leaving the *Drop Down* emits `cm-dropdown-close`, opening it emits `cm-dropdown-open` (REQ-7-18).
- [ ] `REQ-7-16` The whole *Control* is one single Tab stop (REQ-3.11-01): `Tab`/`Shift+Tab` enter and leave the component exactly once, focusing the *Filter*, and the *Drop Down* is part of that component rather than a second stop inside it — while *DropDown mode* holds the keyboard the key is held there instead of released, so an open list is left with `Escape` or `Enter` and the next `Tab` leaves the *Control*; all other interactive parts (*Remove all*, *Select All*, each chip "x") keep their click/mouse behavior and programming focus but are not Tab-reachable (`tabindex="-1"`). *(P0)*
- [ ] `REQ-7-12` The component respects the order of *Items* in which they were created or passed during instantiation. *(P0)*
- [ ] `REQ-7-13` *Chips* are placed in the order specified by the `chipPlaceOrder` option: `unsorted` / `asDefined` / `alphabetical` (REQ-5-02). *(P1)*
- [x] `REQ-7-14` The API provides methods for removing *Items* and adding them back at any place within the existing *Items* hierarchy. *(P0)* — `addItem(spec, place?)` and `removeItem(value)` on `MSelect` and on the facade, both naming positions by *value* so no internal object crosses the API: `place` is `{ parent?, before? }`, where `parent` names the *Group Item* the new *Item* goes under and `before` names the sibling it goes in front of (absent, it goes last). The spec is the one `setItems` takes, `selected: true` included. An addition is judged by whatever is on screen when it arrives — the active query (REQ-3.9) and the selected-*Items* restriction — and a selected addition arrives as a *Chip*; a removal takes the *Item*'s whole subtree, its *Chips*, and the form mirror with it, reports one `cm-selection-change`, and renumbers what follows in the maintained flat order and the *Group* counters. Removing the *Current* *Item* clears the marker; removing under the selected-*Items* restriction keeps the restriction and re-filters, and removing the last selected *Item* returns the control to its default state. A duplicate value (against the tree or inside the added subtree), a place naming no *Item*, a place naming a *Leaf* as `parent`, and a `before` naming another parent's child all throw before anything is attached. `addItem` on a control whose tree was never instantiated throws, pointing at `setItems` (REQ-7-15); `setItems` stays the one-time operation that builds the tree. Tests: group 49.
- [ ] `REQ-7-15` **Lazy loading of Items.** With `delayedLoad: true` the component constructs empty and stays empty until the application calls `setItems(specs)`; with the default `delayedLoad: false` the constructor instantiates `config.items` immediately. Instantiation happens at most once per component instance. *(P1)*
  - Cross-refs: REQ-6-04 (programmatic selection before first focus — preset `selected: true` specs re-seed the Selection Box via `setItems`), REQ-7-06 (Items created at runtime), REQ-3.7-02 (Selection Box always visible yet Items not yet created).
  - Design agreed in the REQ-7-15 resolution note in §11; implemented by group 21 tests.
- [ ] `REQ-7-17` `setItems(specs, selectedValues?)` — public one-time instantiation of the whole *Item* tree. When `delayedLoad` is enabled, the component calls it never; the application calls it (typically in response to `cm-items-request`). A second call throws; later tree adjustments happen by adding/removing *Items* (REQ-7-14). It fully replaces any previous tree: rebuilds the *Drop Down*, resets the *Current* marker, and re-seeds the selection — from the new specs' `selected: true` flags where no `selectedValues` is given, and from that array where one is (REQ-7-20). *(P1)*
- [ ] `REQ-7-20` `selectedValues` — the selection stated as an array of *Item* values, both as the second argument of `setItems(specs, selectedValues?)` (the seed) and as a read-only getter of the current selection. The seed is **authoritative**: given, it alone states which selectable leaves are selected, so a `selected: true` flag outside it selects nothing, and its order fixes the *Chips*' arrival order — which `chipPlaceOrder: 'unsorted'` shows, while `asDefined` and `alphabetical` re-sort them (REQ-5-02). The getter returns the values in that same arrival order, the one order that cannot be derived from the selected state, so feeding it back reproduces the same *Chips*. Both directions carry selectable leaves only: a *Group Item* owns no *Chip* and is selected through its children (REQ-3.3-04), so its value never appears, and its selection is derived from the leaves that do. Resolution is lenient, because the seed is a selection remembered from a previous session and a list that no longer matches the tree should restore what still resolves rather than fail the whole control: a value naming no *Item*, a value naming a *Group Item*, and a repeated value are each warned about (REQ-3.2-11, REQ-8) and skipped, the first occurrence of each value fixing *Chip* order, while a non-array argument still throws. *Item* values are globally unique (REQ-3.2-12), so a value resolves to at most one *Item* and a repeat is unambiguously the same *Item*. It is not the interactive path: nothing here simulates a user selection, each named *Item* is selected through the same act as any other selection (REQ-3.5-01). *(P1)*
- [x] `REQ-7-18` Custom events (prefix `cm-`), `CustomEvent` with `detail`, bubbled on the component root: `cm-items-request` (one-shot when the component is empty — first Filter focus, first *Drop Down* open, first toggle-all/clear-all), `cm-items-set` `{count}` (delayed flow only), `cm-dropdown-open`, `cm-dropdown-close`, `cm-mode-change` `{from, to}`, `cm-selection-change` `{values, added, removed}`. The selection event fires once per settled change — once for `toggleAll()`, `clearAll()`, assigning `selectedValues` or toggling a *Group*, not once per *Item* — after the *Chips*, the visible list and the form mirror are up to date; it stays silent when a settle moves nothing, and a reorder alone reports empty `added`/`removed` because the order is part of the selection (REQ-5-02). *(P1)*
- [ ] `REQ-7-19` Preset-selection safeguard: instantiating more than 50 already-selected *Items* with `maxVisibleChips` left null enforces `maxVisibleChips = 25`, so the selection collapses to the summary chip instead of flooding the DOM with hundreds of individual chips. The cap applies only at instantiation; a selection of ≤50 stays expanded. *(P1)*

## 11. Open questions / items to detail
- **REQ-7-15 (lazy loading) — resolved:**
  - Trigger count: a `delayedLoad` flag (default `false`); with it enabled the component instantiates on the application's `setItems(specs)` call, typically reacting to the one-shot `cm-items-request` event. Instantiation is at most once; a second `setItems` throws.
  - Preset selection (REQ-6-04): preset `selected: true` specs, or the `selectedValues` array (REQ-7-20), re-seed the Selection Box within `setItems`, so chips appear without any prior focus. When preset selection exceeds 50 (REQ-7-19) the box collapses to the summary chip.
  - Runtime adjustments (REQ-7-06/7-14): additions/removals act on the already-instantiated tree; a future extended `setItems` capable of re-instantiation remains possible.
  - Performance intent: avoid upfront instantiation cost and enable deferred data sources (network/backend → `setItems`).
